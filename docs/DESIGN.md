**One line:** photograph a receipt, an LLM itemizes it, friends claim their items, and the app tracks net balances and records settlements through a simulated payment provider.

## 1. Goals and non-goals

Goals (what this project is meant to demonstrate, in priority order):
1. Correctness under concurrency: many users acting on shared state, with measured invariants and negative controls.
2. An async job pipeline that survives worker crashes (leases, fencing, retries, dead-letter), with measured recovery.
3. Idempotent, failure-tolerant settlement against a flaky external provider.
4. Sound authentication/authorization practice (OIDC, group-scoped authz in the application and, as defense in depth, in the database through row-level security; tested for cross-group access).
5. An LLM used as a pluggable, untrusted dependency (validated output, redaction, mockable).

Non-goals / explicitly cut: real money, multi-currency, multi-payer expenses, push notifications, email/SMS invites, application-level encryption of receipts, Kubernetes/Terraform/autoscaling (README "extension path" only), vision-LLM extraction, native Swift/Kotlin.

The ledger records IOUs between friends, not real funds. Never describe it as a financial or payments ledger.

| Allocator (M2.1) | `internal/allocator`, pure Go, stdlib only. `Apportion` is largest-remainder over integer weights using 128-bit multiply/divide (`math/bits`), so `total*weight` cannot overflow. Ties go to the lowest member id (bytewise uuid order); output is sorted by id and independent of input order. `Allocate` splits each item evenly among its claimants, then prorates tax and tip by claimed subtotal. Known property: with equal weights each item's leftover cent goes to the lowest-id claimant, so across k shared items one member can be up to k cents over exact (per item, under 1 cent). A rotating tie-break would spread this but deviates from the "tie-break by member id" rule above; not adopted |
| DB roles (M2.2, migration 00004) | (History: M7 added `fifty_worker` and `fifty_system` and put the application role under row-level security; see the decision-log rows "Worker and system roles (M7.2)" and "Row-level security (M7.4)".) | Ledger schema (M2.2, migration 00005) | Net signed entry per member per ledger transaction (unique on transaction+member, zero rows not stored; payer who also claimed gets one net entry). No stored expense total (derived from items + tax + tip). Kinds `expense` and `void` only; `settlement` is added in M4 together with its link column. Composite foreign keys make cross-group rows impossible: payer, claimant and ledger-entry member must be members of the row's group; a claim's item, expense and group must agree; a posting's expense must be in its group; a void must reverse a posting of the same expense. One `expense` posting and one `void` per expense (partial unique indexes), so a duplicated finalize or void cannot post twice. Zero-sum is a deferred constraint trigger (checked at COMMIT, `SUM` is numeric so it cannot overflow). Entries can only be inserted by the database transaction that created their header (`txid xid8` column + trigger), so a committed posting can never be extended, even with a balanced pair. Append-only: UPDATE/DELETE/TRUNCATE revoked from the app role, plus triggers that refuse them for everyone including the owner and superusers (a superuser can still disable triggers; the claim is protection against bugs and a compromised app, not against the DBA). Not enforced by the database, on purpose: that no claim changes after finalize. A status-check trigger would not close the claim-vs-finalize race (it reads committed state), so that stays with the row locks and the stress test |
| Expenses API (M2.3) | `POST /v1/groups/{id}/expenses` (any member; the creator is the payer; `Idempotency-Key` required), `GET .../expenses` (newest first, at most 100), `GET .../expenses/{expenseId}`. Created in `claiming` with all items in one transaction. The client never sends a total: `total_minor` = items + tax + tip, derived on every read. Limits: 1-100 items, amounts integers 0..100,000,000 minor units, text 1-200 chars trimmed; `price_minor` required (missing is not 0); floats rejected; tax and tip must be 0 if every item is free (finalize could never succeed). Check order: membership (404) -> key (400) -> body (400) -> idempotent transaction, so a non-member learns nothing, not even that their body was malformed. The idempotency fingerprint is the group id plus the validated, normalized request, so equivalent requests replay and the same key in another group is a 422. Reads: one statement joins `memberships` and filters on the path's group; unknown, foreign-group and malformed ids and non-members all get the same 404 (`expense not found`). Detail reads the expense and its items in one REPEATABLE READ snapshot. Items carry `claimed_by` (sorted member ids; `[]`, never null). No audit event on create |
| Claims API (M2.4) | `PUT` / `DELETE .../items/{itemId}/claim`: a member claims or unclaims for themselves only. Naturally idempotent (re-claim is 200, unclaiming a claim you do not hold is 204), so no `Idempotency-Key`. One transaction: the first statement takes `FOR SHARE` on the expense row, authorizes (membership join, path-group filter) and returns the status; any status other than `claiming` is 409 `expense_not_claimable`; then the item is looked up scoped to the expense (404), then the write. `FOR SHARE` is deliberate: compatible with itself (claimers never queue behind each other), conflicts with `FOR UPDATE` (finalize, void) and with `FOR NO KEY UPDATE` (a plain UPDATE, i.e. item edits), which `FOR KEY SHARE` would not. 404 bodies are identical for non-members and for unknown, foreign-group and malformed expense ids; a malformed item id is looked up only after the membership check |
| Finalize (M2.5) | `POST .../finalize`, payer only (the group owner has no special rights), `Idempotency-Key` required, optional `{"split_rest_among": [member ids]}`. Order: path ids, authorization with no write lock (404 non-member, 403 non-payer), key, body and split-list membership (400s, before the key is claimed), then one idempotent transaction: `FOR UPDATE` on the expense row (waits for in-flight claims and blocks new ones, so the claim set read next is stable); status must be `claiming` (else 409 `invalid_state`); unclaimed items give 409 `items_unclaimed` unless `split_rest_among` is given, in which case real claim rows are written for them in the same transaction (so "ledger = recomputed claims" still holds); `allocator.Allocate`; `ledger.ExpenseEntries`; ledger header and entries; expense marked finalized (conditional on `claiming`); `expense.finalized` audit event. Postings are net per member: each non-payer claimant is debited their total, the payer is credited the sum (a payer who also claimed gets only the difference), zero entries are omitted, and a payer who ate everything posts a header with no entries. The response is the finalized expense, `ledger_transaction_id` and per-member `shares`. Every 4xx from inside the transaction is stored and replayed (Stripe model), so a client that gets `items_unclaimed` and fixes it must retry with a NEW key (the OpenAPI text says so). The lock query authorizes by `payer_id` with no membership join, because the foreign key on `expenses (group_id, payer_id)` already makes a payer a member. Core invariant, tested by recomputing from the claims table and not from the response: the ledger holds exactly the entries the claims imply and sums to zero (`assertLedgerMatchesClaims`) |
| Balances and suggested transfers (M2.6) | `GET .../balances` (any member): every current member in join order with `balance_minor` = SUM of their ledger entries in the group (positive: the group owes them), the currency, and `suggested_transfers` (derived at read time; nothing is posted). One statement, so a response is one snapshot: it sums to zero and applying its transfers gives all zeros even while expenses are being finalized. Unfinalized expenses count for nothing. Simplification is `ledger.SuggestTransfers`, a pure greedy: repeatedly the member owed most is paid by the member who owes most, for the smaller amount, ties to the lowest member id; at most n-1 transfers for n nonzero balances, independent of input order. It **reduces** transfers and does not minimize them (the exact optimum is NP-hard): balances -8, -7, +7, +2, +6 need 3 transfers and greedy gives 4 (pinned in a test; worse than optimal in 4 of 3000 random small inputs). Settlements (M4) post to the same ledger, so this endpoint reflects them unchanged |
| Void (M2.7) | `POST .../void`, payer **or group owner**, `Idempotency-Key` required, no body. Same shape as finalize: authorization without a write lock (404 non-member, 403 other members), key, then one idempotent transaction: `FOR UPDATE` on the expense row; status must be `finalized` (else 409 `invalid_state`, including already void); a `void` ledger transaction with `reverses_id` pointing at the finalize posting; the original entries copied with their sign flipped by one `INSERT ... SELECT` (the reversal is the exact negation by construction); the expense set to `void` (conditional on `finalized`); an `expense.voided` audit event (`voided_as`: `payer` or `owner`). Only a finalized expense can be voided: a claiming expense has nothing on the ledger and cancelling it is not in scope. Nothing on the ledger is updated or deleted, claims stay as the record of who had what, and a void expense accepts no claims, unclaims, finalize or second void. Tested: balances after a void equal balances as if the expense had never been finalized, whatever happened in between. A void after a later settlement (M4) can flip a pair's sign; that is correct (see M2 scope decisions) |
| M2 closed early; 2.8 and 2.9 deferred (2026-10-29) | Ryan delegated this call after M2.7. **2.9 (negative-control seams) goes into M5**: M5 already lists negative controls, and the seam is a real design problem that needs the stress harness in view. | Queue schema and enqueue (M3.1, migration 00006) | One `jobs` table, shape per section 6. The database refuses every column combination the state machine cannot produce: `lease_token` and `lease_expires_at` are non-null exactly while `state = 'running'`; `finished_at` is non-null exactly in `succeeded` / `dead`; `attempts <= max_attempts`; the payload is a JSON object. A claim increments `attempts`, so while running it is the current attempt's number. `max_attempts` has no database default: `queue.DefaultMaxAttempts` (5) is the one place the default lives. `queue.Enqueue` takes a `pgx.Tx`, not a pool, so a job cannot be enqueued outside the transaction of the row that needs it (no dual write); `run_at` defaults to the database clock |
| Claim and leases (M3.2, migration 00007) | `queue.ClaimJobs(pool, {Kinds, Limit, Lease})` is one autocommitted statement: a `MATERIALIZED` CTE selects the oldest eligible rows with `FOR UPDATE SKIP LOCKED`, and the `UPDATE` sets `state = running`, `attempts + 1`, a **new** `lease_token` (`gen_random_uuid()`, so every claim is a new fencing token) and the lease expiry, all on the database clock. A worker names the kinds it has handlers for; there is no "any kind". It takes the pool, so row locks last one statement; what keeps other workers off a running job is the lease, not a lock. **Eligibility is one timestamp:** while a job runs, `run_at` equals `lease_expires_at` (a CHECK keeps them equal), so "claimable" is `state IN (queued, running) AND run_at <= now() AND attempts < max_attempts`, covering both a due queued job and a running job whose lease expired, served by one partial index `jobs_claim_idx (run_at)`. Reason, measured on 200k rows (temp table, Postgres 17.11, one run, not a benchmark): the first design (two partial indexes, `OR`) made the planner read and sort every due row, 11.9 ms per claim and growing with the backlog; the single-timestamp form is an ordered index scan that stops after `LIMIT` rows, 0.03 ms. Costs accepted: each heartbeat changes an indexed column, so it cannot be a HOT update, and a large backlog of a kind nobody handles slows every claim. A job whose last attempt's lease expires is not claimable; `queue.ReapExhausted` moves it to `dead` with `last_error = 'lease expired on attempt N of N'` (the worker calls it periodically; safe against a worker that completes late, since both are conditional UPDATEs that serialize on the row). `ORDER BY` and `MATERIALIZED` are kept as the contract even though Postgres 17 would behave the same without them |
| Fencing, completion and failure (M3.3) | A worker's only writes to a job it holds are `Heartbeat`, `Complete` and `Fail`, each one conditional UPDATE on `id` and `lease_token`. A stale worker (its lease expired and another claim wrote a new token) matches no row and gets `ErrLeaseLost`, with nothing changed. There is deliberately no `state = 'running'` in them: the CHECK makes `lease_token` non-null exactly while running, so a matching token already implies running (if that CHECK is ever relaxed the condition must come back). **`Complete(tx)` must be the last statement of the transaction that makes the handler's effects**, and `CompleteWith(pool, claimed, fn)` is that shape: `fn` writes, then `Complete`, then commit. If `fn` errors, everything rolls back and the job stays running under the same lease (the caller then calls `Fail`); if the lease was lost, everything rolls back and `ErrLeaseLost` is returned, so a stale worker's effects never exist. Why last: the completion's row lock stops any claim taking the job until commit, and it is the fence check at the latest possible point; completing first would hold the row lock through the whole handler and block heartbeats. `Fail` runs on the pool after the attempt's transaction rolled back: the job goes back to `queued` after `RetryIn` or to `dead` when `attempts = max_attempts`, with `last_error` (cut to 2000 bytes on a character boundary). `Heartbeat` extends `lease_expires_at` and `run_at` together, and succeeds on a lease that expired but was not taken over. Exactly-once covers only writes inside the handler's Postgres transaction; the LLM or provider call is at-least-once |
| Retry policy and requeue (M3.4) | `FailParams.RetryIn` is a duration applied as `now() + interval` in SQL, not a worker-supplied timestamp, so clock skew between workers cannot make retries early or late. `queue.Backoff{Base, Max}.Delay(attempt, rand)`: ceiling `min(Max, Base * 2^(attempt-1))`, delay uniform in `[0, ceiling]` (full jitter). Chosen because it spreads a crowd of jobs that failed together (a 429 burst) best; the cost is that a retry can come back almost immediately, so a dependency needing a guaranteed pause needs a larger `Base` or "equal jitter". `DefaultBackoff` is 2 s base, 5 min cap: **placeholders, not tuned**. Overflow-safe for any attempt number; the randomness is injected so tests are deterministic. A worker crash does not use backoff: its lease expires and the next claim is the next attempt at once; when the last attempt's lease expires the reaper dead-letters the job. **`queue.Requeue` and `worker requeue --kind K` / `--id ID...`** give dead jobs a fresh set of attempts: `queued`, due now, `attempts` back to 0 (a dead job has `attempts = max_attempts`, which the claim refuses), `last_error` kept as the record of why it died. Only dead jobs match; at least one of kind or id is required (there is no "all"), and with both a job must match both. It prints one id per line |
| Worker runtime and periodic jobs (M3.5, migration 00008) | `worker.Run(ctx, Config)` is one worker process; any number can share a database. **Handlers are two-phase:** `func(ctx, job) (Commit, error)`. Phase one does slow or external work (an LLM or provider call) with no transaction open and returns an optional `Commit(ctx, tx)`; phase two runs inside the transaction that also marks the job succeeded (`queue.CompleteWith`), so the handler's database effects and completion commit together and no transaction is held open across an external call. Only phase two is exactly-once; phase one may run more than once, so any external effect must be idempotent (a provider call keyed by the settlement id, M4; not the job id, which changes when a watchdog or an operator enqueues a fresh job for the same settlement). **Loop:** claim into free slots only (`Limit = free`), at most `Concurrency` jobs in flight, wait `PollInterval` when the queue is empty or a slot frees, claim only kinds with registered handlers. **Per job:** a heartbeat goroutine extends the lease every `Lease/3`; if the heartbeat finds the lease taken over it cancels the handler's context with cause `queue.ErrLeaseLost` and the worker reports nothing (the new holder's attempt counts). A handler error, a panic (recovered, stack logged, never stored) or a failed `Commit` fails the attempt: retried after `Backoff.Delay`, or dead-lettered on the last attempt. **Shutdown (SIGINT/SIGTERM):** stop claiming, let in-flight jobs finish for up to `ShutdownGrace` (jobs run on a context detached from the signal), then cancel stragglers and hand them back at once (`queued`, due now, `last_error = 'worker shut down mid-job: ...'`, no backoff; the attempt is still counted). **Housekeeping:** every `ReapInterval` the reaper dead-letters jobs whose last attempt's lease expired. **Periodic jobs:** migration 00008 adds `jobs.dedupe_key text UNIQUE`; `queue.EnqueuePeriodic` inserts `kind:floor(epoch/every)` with `ON CONFLICT DO NOTHING`, the period computed on the database clock, so any number of workers produce exactly one job per period. A self-rescheduling job was dropped because one dead-lettered run would end the chain for good. A lost period's job is not repaired. **`idempotency.cleanup`** (hourly, 3 attempts) deletes expired `idempotency_keys` in batches of 1000 until a batch deletes nothing (not "until a short batch": a concurrent cleaner can make a batch short while work remains). The DELETE repeats the expiry test on the outer statement: `ClaimIdempotencyKey` takes over an expired row by UPDATEing it live, and a DELETE that selected the row earlier waits, sees the new version, and Postgres re-checks only the DELETE's own conditions, not the subquery's. Defaults: 4 jobs, 30 s lease, 1 s poll, 20 s grace, 10 s reaper, 1 min periodic check; `MinLease` 30 ms. The reaper and cleanup are global, so tests in different packages (run in parallel) can do each other's work; those assertions check end states, not who did it |
| Metrics (M3.6, migration 00009) | `worker run --metrics-addr HOST:PORT` serves Prometheus text format at `/metrics` (off by default; hand-written, no client library). **No authentication**: it reports job counts by kind and nothing else (no payloads, ids or error text); bind it to a private interface. **Two kinds of metric, split by where the truth lives.** Gauges come from the database at scrape time, so every worker reports the same: `fifty_queue_jobs{kind,state}` with disjoint states `ready`, `delayed` (queued for later), `running` (live lease), `expired` (lease run out, awaiting takeover or the reaper) and `dead`; and `fifty_queue_oldest_ready_age_seconds{kind}` (0 when none; delayed jobs do not count), the number to alert on for a stuck queue. One statement, so one snapshot, reading only small partial indexes (`jobs_claim_idx`, `jobs_dead_idx`): 0.5 ms on 200k rows (temp table, one run, not a benchmark), independent of finished-job volume. Counters are per worker process and reset on restart: `fifty_worker_jobs_finished_total{kind,outcome}` (`succeeded`, `failed_retry`, `failed_dead`, `lease_lost`) and the histogram `fifty_worker_job_attempts{kind}` (buckets 1, 2, 3, 4, 5, 10, +Inf), observed only on the deciding attempt (counting every retry would count one job several times). A failure that could not be reported is not counted. Every handled kind always reports every series, at zero when idle, so an alert on a quiet series does not silently never fire |
| Mock LLM (M3.7) | `cmd/mockllm` over `internal/mockllm`. Wire format: the Anthropic Messages API subset a client needs (`POST /v1/messages`, the message envelope, `{"type":"error","error":{...}}` bodies, `retry-after`), so the M6 receipt client and the benchmarks share one code path; it validates `model`, `max_tokens` and `messages` (400 otherwise) but never reads the prompt and always returns the same canned text, except in fixture mode (M6.5, see decision log "Generator and fixture mode"). Latency: log-normal, `median * exp(sigma * z)`, default median 800 ms, sigma 0.4 (p99 about 2.5x the median); sigma 0 is a fixed delay. Applied to successful and malformed responses only; 429 and 5xx answer at once, which is the optimistic case and must be stated in any retry-benchmark writeup. Faults: each request draws one outcome (timeout, 429, 5xx, malformed, else success), so rates are mutually exclusive and must sum to at most 1; 5xx is 500 or 529 (`overloaded_error`); malformed is a 200 whose body is cut in half; a timeout holds the connection (`--timeout-hold`, default 1 min) and then aborts it with no response (returning normally would send an empty 200). Draws come from one seeded generator under a lock: the same seed gives the same sequence of draws, but under concurrency which request gets which draw depends on arrival order, so rates are reproducible and exact fault sequences are not. Benchmarks record the configuration and the observed counts (`GET /stats`), not only the configured rates. A retry redraws, as against a real API. No authentication, loopback by default. Fixture mode (M6.5) answers a `REF n` token with a stored reply; the real client is tested against it (M6.8). Not built: streaming |
| Recovery test (M3.8a) | `internal/benchwork` + `cmd/benchworker`. The workload is a test-only job kind, `mock.extract`: phase one POSTs to the mock LLM (no transaction), phase two inserts one row in `bench.effects` inside the completion transaction. The `bench` schema (`attempts`, `effects`) is created by the harness with the owner role, not by a migration, so the product schema carries nothing that exists for benchmarks, and the production worker does not register the kind. The harness starts N real `benchworker` processes, waits for the victim to reach a kill point, sends SIGKILL (and checks the process died by that signal), lets the survivors finish, and reads the outcome from Postgres: lost jobs (jobs - succeeded), duplicate effects (rows beyond one per job), missing effects, extra attempts, and per-orphan recovery time (kill until success, both timestamps from the database clock). Kill points: `call` (victim saturated, jobs waiting on the LLM) and `commit` (an effect row inserted in a transaction held open by `--commit-delay`; the worker records `commit_started_at` outside that transaction so the harness can kill exactly then). The `commit` point is what tests atomicity: a handler that wrote its effect outside the completion transaction produces a duplicate effect there. Time to recovery includes queueing: an orphan becomes claimable when its lease expires, and claims go in `run_at` order, so any backlog of older jobs runs first; a benchmark must state its backlog (jobs vs worker slots). ## 3. Architecture

docker-compose services:

- `api`: Go HTTP server (REST/JSON). Validates JWTs, enforces authorization, owns all writes.
- `worker`: Go binary from the same module. Runs queue consumers (receipt parsing, settlement execution, reconciliation).
- `postgres`: primary store, queue, idempotency keys, audit events.
- `dex`: OIDC provider with static users.
- `mock-llm`: standalone Go HTTP server using the real provider's wire format; configurable latency distribution, 429/5xx/timeout rate, malformed-JSON rate; deterministic output from synthetic ground truth.
- `mock-payments`: standalone Go HTTP server; configurable latency, failure, timeout-after-success, duplicate/out-of-order webhooks (HMAC-signed).
- Receipt image storage: behind an `ObjectStore` interface; the backend is a filesystem directory (decided at M6, decision log "M6 plan decisions"). MinIO is the extension path.

Mobile app (`mobile/`, Expo) talks only to `api` and Dex (system browser for login).

As built through M8, compose runs only `postgres` and `dex`; `api`, `worker`, `mockllm` and `mockpay` run on the host (`make run-api`, `go run ./cmd/worker run`, `go run ./cmd/mockllm`, `go run ./cmd/mockpay`), `tesseract` is a program installed on the host (`brew install tesseract`), and the mobile client is built and served from the host by Expo (`npx expo run:ios` in `mobile/`). Containerizing the rest is not built and is not needed for the milestones that remain.

## 4. Domain model (conceptual)

- `users` keyed by (issuer, subject); provisioned on first valid token.
- `groups` (one currency), `memberships`, `join_codes` (hashed, expiring, revocable, use-limited).
- `expenses`: payer, totals, status, `version`.
  - Status: `parsing` -> (`needs_review`) -> `claiming` -> `finalized` | `void`. `needs_review` -> `claiming` is the payer's `confirm`. A receipt that cannot be read (extraction fails for good, or never validates) also ends in `needs_review`, with no items, so the payer enters them by hand with item edits; there is no failed status.
  - An expense can also be created directly with items (needed for stress tests and manual entry); receipt upload is one way to produce items.
- `expense_items`, `claims` (unique per item+member).
- `ledger_transactions` (kind: expense | settlement | void) and `ledger_entries` (signed amounts per member). Append-only.
- `settlements`: status `pending` -> `succeeded` | `failed` | `unknown`, and `unknown` -> `succeeded` | `failed`; `succeeded` and `failed` are terminal. A contradicting late event is recorded, not applied (decision log, "M4 plan decisions").
- `idempotency_keys`: scoped per user, with request fingerprint and stored response.
- `jobs`: see section 6.
- `audit_events`: finalize, void, settle, membership changes, join-code use.

## 5. Ledger and concurrency

Money: int64 minor units, CAD/USD only (2 decimals). No floats anywhere.

Postings:
- Finalize: payer is credited the expense total; each claimant is debited their share (payer included if they claimed items). Entries sum to zero per transaction.
- Settlement success: the sender (who owes) is credited and the payee debited by the settled amount, so the sender's balance rises toward zero. Say "sender", not "payer": "payer" already means the payer of an expense.
- Void: reversing entries for the original transaction.
- Group net balances = SUM over entries; they always net to zero. Suggested transfers come from simplification (greedy over net balances, read-time, suggestions only; reduces transfer count, does not minimize).

Share calculation:
- Shared items split evenly among claimants; remainders by largest-remainder with deterministic tie-break (member id).
- Tax and tip are prorated by each member's claimed subtotal using the same allocator.
- Property tests assert: shares always sum exactly to the total; allocator is deterministic.

Concurrency (READ COMMITTED + targeted locks; SERIALIZABLE is not used):
- Claim / unclaim: `FOR SHARE` on the expense row, then verify status = `claiming`. Concurrent claimers don't block each other.
- Finalize / void: `FOR UPDATE` on the expense row. Finalize waits for in-flight claims, then reads a stable claim set. Claims arriving after wait, see `finalized`, and are rejected (409). Item edits and confirm take `FOR NO KEY UPDATE` (the strength the version bump takes anyway; it conflicts with the claimers' `FOR SHARE`, with `FOR UPDATE` and with itself, but not with the foreign-key checks' `FOR KEY SHARE`).
- Item edits (payer only, M6.1) use the `version` column as an optimistic lock: the client sends the version it read, the edit takes the row lock, compares, and a mismatch is 409 `version_conflict` with nothing written; the last write is a conditional update on the version read under the lock. Version goes up by one on every edit and on confirm, and not on claims (a claim must not make a payer's edit stale; an edit deletes the claims it invalidates instead). Decision log "Item edits (M6.1)".
- Settlement creation: validated under a per-group lock (`FOR NO KEY UPDATE` on the group row; `FOR UPDATE` would block foreign-key inserts). The ledger has net balances, not pairwise debts, so the rule is `amount <= min(-balance(from) - reserved_out(from), balance(to) - reserved_in(to))`, reserved = the member's `pending` and `unknown` settlements. The lock serializes settlement creation only, not finalize or void. Success posting does not re-validate (it records a payment that already happened). Details: decision log, "M4 plan decisions".
- DB-enforced invariants: unique constraints, deferred constraint that each ledger transaction sums to zero, app role has no UPDATE/DELETE on ledger tables (plus a trigger and a test).
- Considered, not adopted: bumping `version` on every claim so finalize is a compare-and-swap on the reviewed state. It would serialize claimers on one row. Revisit if UX needs it.

Idempotency: required `Idempotency-Key` header on create-expense, edit-expense, confirm, finalize, void, create-settlement, join-group (and, from M6.6, receipt upload).
- Same key + same fingerprint: replay the stored response (a concurrent duplicate waits on the unique index and then replays).
- Same key + different fingerprint: 422.
- Keys expire after 24 h.
- Implemented (M1.3) as `internal/idempotency`: the key row is claimed in the same transaction as the operation and completed before commit, so effects, stored response and key commit or roll back together (no "in progress" state). Every response below 500 is stored and replayed, including business-rule 4xx (Stripe model: a key's first outcome is final). 5xx and errors roll back and are not stored, since the transaction is atomic and a retry should be able to succeed. Validation errors, 401 and 429 are rejected before the key is claimed. Handlers that return a non-2xx result must not have written anything they don't want committed.

Negative controls: nine protections can be switched off, **only in a binary built with the `unsafe_controls` tag**: the claim, finalize and void row locks, the idempotency check, the settlement group lock, `Resolve`'s row lock and the guards on its status updates, and (since M6.2) the item-edit row lock and the version comparison of edits and confirm (`internal/controls`, decision log "Negative-control seams (M5.1)"). There is no runtime flag in the production binaries, and a test proves they contain none of the code. A control removes exactly one protection; the others stay, so a run reports which layer caught what: the database has backstops behind several (the unique one-posting-per-expense and one-posting-per-settlement indexes, the conditional status updates, CHECK constraints), and none behind others (a claim racing a finalize: DESIGN row 45 says so on purpose). The report says, for each control, the anomalies by invariant and the errors by constraint. Measured in M5.4: on the settlement success path the layers are `Resolve`'s row lock, then the unique posting index, then the guard on the status update. The edit lock and the version-check control (M6.2) are NOT part of the M5 numbers; CLAIMS rows must say exactly which protections were disabled.

## 6. Job queue

Single `jobs` table: kind, payload, state (`queued` | `running` | `succeeded` | `dead`), attempts, max_attempts, run_at, lease_token, lease_expires_at, last_error.

- Claim: one statement selects eligible rows (`queued` and due, or `running` with an expired lease) with `FOR UPDATE SKIP LOCKED`, sets a fresh lease token and expiry, increments attempts. While a job runs, `run_at` is its lease expiry, so eligibility is the single condition `run_at <= now()` (M3.2 decision log).
- Heartbeat extends the lease only if the token still matches.
- Completion/failure writes are conditional on the lease token (fencing). A stale worker cannot overwrite a newer attempt.
- Handler effects and job completion commit in one transaction, so effects are exactly-once with respect to Postgres. The LLM/provider call itself is at-least-once (may be billed twice on retry); this is documented, not hidden.
- Retries: exponential backoff with jitter up to max_attempts, then `dead` (dead-letter state with requeue by an operator command).
- Enqueue happens in the same transaction as the row that needs the job (no dual write).
- Metrics: queue depth, oldest-job age, attempts histogram, exposed on a metrics endpoint (built, see the decision log).
- Housekeeping jobs: expired idempotency keys are deleted hourly; succeeded jobs older than 7 days are pruned hourly; dead jobs are kept for an operator.
- `LISTEN/NOTIFY` to wake workers instead of polling: measured in M3.8d and not built (decision log, "LISTEN/NOTIFY").

Why not River/SQS/Kafka (be ready to say this in an interview): transactional enqueue with no extra infrastructure; the mechanism is the point of the exercise; River would hide it. Trade-off accepted: a Postgres queue won't scale to very high job rates, and the README will say so.

## 7. Settlement flow

1. `POST /v1/groups/{id}/settlements` with `Idempotency-Key` (the caller is the sender; body: `to`, `amount_minor`): validate under the group lock, insert `pending`, enqueue `settlement.execute` and write the audit event in the same transaction, return 202. Clients poll `GET .../settlements/{id}`.
2. Worker, phase one (no transaction open): call the mock provider with the settlement id as the provider idempotency key.
3. Outcomes, applied in phase two by `settlements.Resolve` in the transaction that also completes the job: success -> settlement `succeeded` + ledger posting. Definite failure (declined) -> `failed`. Timeout or any ambiguous result -> `unknown` and a `settlement.reconcile` job in the same transaction; execute never re-sends. Reconcile reads the payment from the provider by key (re-sending the same create if the provider has none) and calls `Resolve`; while the provider has no final answer it enqueues its own next check (explicit `run_at`, counter in the payload) until a deadline, after which the settlement stays `unknown` for an operator. A watchdog periodic job re-enqueues execute for settlements stuck in `pending` (safe: the provider call is keyed).
4. Provider webhooks (`POST /v1/webhooks/payments`, HMAC over timestamp + body, timestamp tolerance) may arrive duplicated or out of order and call the same `Resolve`. Transitions are monotonic: a repeat is a no-op, a contradiction of a terminal state is recorded as `settlement.conflict` and not applied.
5. Ledger posts exactly once per settlement, only on confirmed success: `Resolve` locks the settlement row (`FOR UPDATE`) before deciding, and a unique partial index on `ledger_transactions (settlement_id)` is the database's backstop.

Mock provider fault injection: latency, definite failures, timeout after the charge succeeded, duplicate webhooks, out-of-order webhooks.

## 8. Receipt pipeline

upload -> hardening (size/dimension limits, sniff real content type, strip EXIF, re-encode; built, M6.6) -> store (built, M6.6) -> `receipt.parse` job:
Tesseract OCR (built, M6.9a) -> regex redaction (card numbers, phones, emails; names are not redacted) -> `Extractor` (text LLM via provider interface; mock or Anthropic) -> JSON-schema validation -> reconciliation check -> items written, expense moves to `claiming` (or `needs_review`).

- Review flag is deterministic: schema valid and items + tax + tip == total within tolerance. LLM self-reported confidence is not used.
- `needs_review`: the payer edits items (`PATCH`, optimistic lock) and then calls `confirm`, which opens the expense for claiming. Extraction that fails for good, or never validates, also lands here with no items (decision log "M6 plan decisions"). A job the reaper dead-letters without telling the expense would leave it in `parsing` for ever; the sweep (`receiptparse.SweepHandler`, built in 6.7) moves such expenses to `needs_review` with reason `parse_abandoned`.
- Quantity lines (e.g. 3 x beer) are expanded into per-unit items so units can be claimed individually (the extra minor units go to the first units, the same split `allocator.Apportion` gives equal weights over ids in unit order). Settled at M2: the expense API only accepts per-unit items; the helper is `receipts.ExpandQuantity` (M6.4).
- Prompt injection: receipt text is untrusted. The model has no tools; output is schema-validated and reconciled; worst case is a wrong parse the user reviews. Injection fixtures live in the test suite.
- Per-user rate limit and daily receipt quota (also caps LLM cost).
- Synthetic receipt generator renders receipts from known ground truth (items, totals, planted PII, noise/skew). It feeds the OCR/redaction evals, the accuracy eval, mock LLM responses, and the demo (print or display receipts and photograph them).

The idea: send a read as one pipelined batch (`set_config` for the identity and, in the same call, `transaction_read_only`, then the statement; the implicit transaction ends at the batch's Sync), wrapping the batch's rows so sqlc's `defer rows.Close()` ends it. Writes keep their explicit transactions (they already pay little: about 9% for the seam in the recording). Risk: it changes the code every read goes through; coverage is `internal/dbscope` (the identity must not outlive the statement, the connection must be released on every path, writes must be refused), `test/rls`, the whole suite and the stress run. Whatever is done, re-record `bench/rls` and keep both recordings.
- Dead jobs are never pruned (only `succeeded` ones are): an unattended dead-letter queue grows until an operator requeues or deletes. Alert on the `fifty_queue_jobs{state="dead"}` gauge. A manual delete command is not built.
- A claim whose client cancels mid-flight (worker shutdown) can lease jobs that no one runs: the statement committed but the worker never saw the result. They are retried after the lease expires with the attempt counted; on a job's last attempt the reaper dead-letters it. Rare, and the same outcome as a crash.
- Lock timeouts: a concurrent duplicate waits on the idempotency unique index with no timeout if the first request stalls, and a claim waits without a bound for a stalled finalize/void/edit holding `FOR UPDATE` on the expense row. Add `lock_timeout` when hardening.
- `GET /v1/groups/{id}/balances` is O(ledger entries in the group) per request. Fine at this project's sizes; a cached running balance would need the zero-sum and derived-by-SUM invariants re-proved.
- `suggested_transfers` come from the ledger only and ignore pending settlements, so a member may be shown a transfer that create-settlement would refuse because the amount is reserved. Documented, not changed.
- Settlements cannot be cancelled while `pending` or `unknown`; a stuck `unknown` past the reconcile deadline needs an operator.
- The rate limit is per api process; revisit if more than one api instance is ever run. The metrics endpoint is unauthenticated (off by default).
- Automated tests missing: the `OIDC_DISCOVERY_URL` issuer/discovery split (implemented, untested; matters when the api runs in a container) and the PKCE login against Dex (only `scripts/dev-token.sh` and manual logins in the app exercise it; CLAIMS row 6 stays `planned`).
- Migration 00004's Down drops the cluster-wide role `fifty_app`, and 00015's drops `fifty_worker` and `fifty_system`; that fails if another database in the cluster still has privileges for them. Roles are cluster-global, so anything that `ALTER ROLE fifty_app` leaks across databases.
- sqlc maps `ledger_transactions.txid xid8` to `pgtype.Uint64`; no query selects it. If one ever needs to, check the scan.

**Tests, development database and measurement notes**
- Tests skip without `TEST_DATABASE_URL` (and the owner-role ones without `TEST_OWNER_DATABASE_URL`) unless `REQUIRE_DATABASE=1`, which CI sets. By hand, export both in the same shell command and confirm with `-v` that tests ran. `make test`, `make test-unsafe` and `make ci` set them; `make test-controls` and `make test-e2e` need `E2E=1`.
- The integration-test database is shared and the tests never clean it (`make reset` does), and `httptest` issuer URLs are random local ports that get reused, so tests create their own identities and compare counts against a baseline taken after setup.
- A test or benchmark process that is killed mid-run (an interrupted `go test`, a Ctrl-C) can leave a scratch database `fifty_e2e_<hex>` in the cluster; `DROP DATABASE ... WITH (FORCE)` removes it (one was left by a hung run during M7.4).
- Dev-database debris: the development database was reset on 2026-11-07 (`make reset`) because old benchmark and stress runs had left about 24,000 settlements in it, 9,000 of them `pending`: a worker with `PAYMENTS_URL` paid them all against the mock and queued new settlements behind them (some of those jobs failed on `ledger_transactions_one_settlement_posting`; not investigated). Run benchmarks and process tests on scratch databases and start a demo from a fresh database.
- The benchmark workload's `bench` schema and `mock.extract` rows are created in the dev database by `benchwork.Setup` (as the owner, not a migration) when the recovery tests or benchmarks run, and the recovery tests leave rows behind. This grows the jobs table whose size the benchmarks record.
- Unexplained replays in the settlement benchmark (CLAIMS row 19): the provider saw 21-36 replayed create calls per run in two mixes although execute never resends. Likely cause: Go's `net/http` transparently retrying a request that carries an `Idempotency-Key` when the provider aborts a reused connection. Not verified for the recorded runs; harmless to correctness, but the create-call counts include them.
- The stress vacuity check `race_mixed >= 1` was wrong for the `claim_lock` control and a weak floor elsewhere (two recorded `claim_lock` runs are flagged because of it, CLAIMS row 2). Fixed in M6.2 and then again after 6.3 (floor 1; decision log "Edit seams and stress (M6.2)" and "Stress re-record (M6.3)"); the recorded files are unchanged and still say DOES NOT MATCH for those two runs.
- `make test-unsafe` (the tagged suite) runs in CI; `make test-controls` (about 6 minutes, real processes) does not. The `unsafe_controls` build must never be used for a release binary.
