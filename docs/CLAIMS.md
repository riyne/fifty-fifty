## Claims that must NOT be made

- Real money movement, production use, "payments platform", "banking-grade". Settlement is **simulated**.
- Any load figure not produced by a recorded run. Benchmarks against the mock LLM must say "mock LLM with simulated latency of X ms".
- "Minimizes" transfers. Debt simplification is a greedy heuristic and **reduces** them (a counterexample where it uses 4 transfers and 3 suffice is pinned in `internal/ledger/transfers_test.go`; on random small inputs it exceeded the true minimum in 4 of 3000 cases).
- PII "removal". Only regex redaction of specific patterns (card numbers, phones, emails) is implemented; names are not redacted. Redaction recall (row 9) is a synthetic-data number: never quote the 100% on ground-truth text without the OCR figures beside it, and never as a statement about real receipts or photographs. Emails are the weak spot once OCR distorts the text.
- Resistance to prompt injection, "safe against a malicious receipt", or any behavior of a real model on adversarial receipts. What exists (row 23) is validation of a model's output and an arithmetic review flag; the injection fixtures are made-up outputs, and the mock model never reads its prompt. A real-model look at injected receipts can only happen in the M9 accuracy evaluation.
- That a receipt "adds up" means the extraction is right: a model can misread a price and the total together, or read prices and total consistently wrong; the review flag catches disagreement between the numbers, not a consistent misreading.
- Encryption at rest of receipts (envelope encryption was cut from scope).
- Kubernetes, Terraform, autoscaling (README extension path only, not built).
- Vision-model extraction, Flutter, Swift/iOS-native, multi-currency, push notifications.
- "Tested on Android", on a physical device, or with the camera: none was run. The iOS client was run by hand on the simulator only (row 12). "Automated UI tests" and a "tested login flow" are also not claimable (row 6 stays `planned`).
- That row-level security makes the system "secure", "tenant-isolated" or "multi-tenant safe": it limits the user-request path to the caller's groups (row 11) and nothing else. The worker, the payment webhook and first-login run as other roles that see everything their grants allow; the identity is a setting that code running as the application role can set to anyone; the table owner and superusers bypass it; `jobs` is outside it. An RLS overhead figure other than the recorded one in row 11, and that one only for its mix, data and machine at the database layer: not "RLS costs X%" in general, and never the policies' cost without the seam's beside it.
- Mutation-testing counts or "N mutations caught" figures. During M2 each lock, check and authorization condition was broken on purpose and a test confirmed failing, but with throwaway scripts that are not in the repo, so the counts cannot be reproduced. The reproducible evidence is the tests themselves (rows 7, 13-16).
- Accuracy numbers from synthetic receipts presented as real-world accuracy.
- That the review flag "catches wrong parses" in general, or any figure for it without its limits (row 10): on this synthetic data it caught 43 of 46 receipts with a wrong amount and none of the 8 with a wrong quantity (arithmetic cannot see a quantity error), and a model that fills an unreadable price so the sum matches the printed total hides the amount error from it (all 3 silent amount errors). The catch rate describes this model, this prompt, this noise and these receipts. Nor "the model is x% accurate": most of the errors at higher noise start in the OCR text, not in the model, and the variants are not independent samples.
- Any prompt-injection result from the accuracy evaluation: no injected receipt was sent.
- The `throughput-queue` figure as "what Postgres can do" or as the queue alone: it includes a local HTTP call and an insert per job, and the workers, mock, harness and Postgres share one laptop. Any queue figure for a real LLM, another machine, or more than 4 jobs in flight per worker.
- "Time to resolve an unknown settlement" as a property of a payment provider or of the system in general: it is set by the reconcile schedule constants (placeholders) and the mock provider's delays.
- Real payment processing, charges, or any settlement figure not from a recorded run against the mock provider.
- A throughput, latency or capacity figure from the stress runs (the api, the workers, the mock provider, the harness and Postgres share one machine, and the run is sized for contention, not load). "The protection is necessary" or "unnecessary" from a control that showed no violation: it shows only that this workload did not get past it. That the production build is "safe" or "correct": it kept the listed invariants in 3 runs of this workload.
